Nesse semestre em Sistemas Corporativos, entendemos o porque do java existir.: a JVM faz o mesmo bytecode rodar em qualquer sistema operacional. Logo apos aprendemos a parte sobre a escolha da arquitetura do nosso sistema. Monólito é tudo numa aplicação só, microsserviço é dividir em serviços pequenos, cada um tendo o seu próprio banco. Tudo depende do contexto e de qual vai suprir melhor as necessidades do nosso sistema.
Para decidir o tamanho de um serviço, é importante respeitar a regra é que ele tenha uma responsabilidade só, que um time pequeno consiga cuidar dele sozinho e que as partes que mudam juntas fiquem juntas. Acessar o banco de outro serviço é o pior tipo de acoplamento, então cada serviço tem o seu.
A parte de APIs REST ensina que o verbo é a ação. GET lê, POST cria e devolve 201, PUT substitui, DELETE remove. E o status code faz parte do contrato, então retornar 200 em tudo é um erro.
No spring boot, o Controller só recebe a requisição, a Service tem a regra de negócio e o Repository cuida dos dados. Também aprendi a não expor a Entity direto: uso DTOs de entrada e saída, com validação (@NotBlank, @Positive) e tratamento de erro centralizado com @RestControllerAdvice.
O JPA, veio para tirar a necessidade de escrever todo o SQL na mão. A classe vira uma @Entity, e o Repository vira uma interface que estende JpaRepository, sem implementação nenhuma: o Spring gera o CRUD sozinho. Em relacionamentos, a Foto ganhou um @ManyToOne no lugar do imovelId solto, então o banco passou a garantir que o imóvel existe.
Nas ultimas aulas aprendemos sobre  o Flyway: em vez de deixar o Hibernate alterar o banco sozinho, cada mudança vira um arquivo versionado, por exemplo o V1__criar_tabela_imoveis.sql. É uma boa prática usar pois irá deixar o banco de dados do nosso sistema de controle do programador, permitindo alterar e versionar o código sem problemas. Ate porque Migration aplicada não se edita, só se cria uma nova.
